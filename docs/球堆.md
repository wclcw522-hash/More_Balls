# 球堆

> 打出去一组球、回收回来一堆耐久各异的球，各自占一格 —— 球堆就是解决这个的。

## 为什么会有这个问题

球的耐久记在数据组件 `toughness_left` 上（**没带这个组件 = 满耐久**）。
而 Minecraft 的堆叠判定要求**两个物品堆的全部数据组件完全一致** ——
所以「挨过 3 次」和「挨过 4 次」的球**必然分成两堆**。

副手打出去一组、靠【空气动力球】回收回来时，每颗挨的碰撞次数都不一样，
几乎不会有两颗同耐久：**一趟下来背包被吃掉大半，而且越用越散。**

## 球堆是什么

给用过的球套一个「壳」。

- 壳是**一件物品 + 一个数据组件**（`ball_cluster` / `BALL_CLUSTER`）
- 内部存**真实的球列**（每颗带自己精确的耐久）—— **取出时把原来那颗还回去，耐久一分不差**
- 一个壳最多装 **64 颗**，**自己只占一格**
- **满耐久的球不套壳**（它们本来就能和同批新球叠成一堆）

> **壳与壳之间不能互相叠。**
> 因为球列本身就是组件的一部分 —— 两堆只要有一颗的耐久不同，组件就不一致。
> 但这不影响目的：**一个壳装完一批就够占一格**。
> 这和潜影盒同理：装满的潜影盒之间也叠不了，但它本来就只占一格。

## 五档（只影响显示，不影响分组）

**档位是按剩余耐久算出来的标签，不存储**：

| 档 | 耐久区间 | 名字里的前缀 |
|---|---|---|
| 完整 | 100%（满） | 不套壳（满耐久的球本来就能叠成一堆） |
| 瑕疵 | ≥ 80% | 「瑕疵的」 |
| 破损 | 50% – 80% | 「破损的」 |
| 残缺 | 20% – 50% | 「残缺的」 |
| 将碎 | < 20% | 「将碎的」 |

> ⚠️ **1.1.0.10 起，档位不再参与「哪些球能进同一个壳」的判断。**
>
> 先前是「同球种 **+** 同档位」才进一个壳，于是同一个球种会被拆成最多 5 个壳
> —— 打完一局回收回来是「好几个各装一两颗的壳」，看着就不像收纳。
> 现在**只按球种分**：一个球种一个壳，里面的球耐久各不相同。
>
> 档位现在只用于两件事：**壳的名字**（取最低那颗的档）、**tooltip 的「最低耐久」**。

按「当前耐久 ÷ 上限」分档（作者指定）：

| 档位 | 区间 | 备注 |
|---|---|---|
| 完整 | 100% | **不进壳** |
| 瑕疵 | 80% ~ 99% | **正好对齐切割门槛（≥80%）**，一眼看出哪堆能上切石机 |
| 破损 | 50% ~ 80% | |
| 残缺 | 20% ~ 50% | |
| 将碎 | 0% ~ 20% | |

**档位是算出来的，不是存的** —— 需要时拿当前耐久现算，不存在「改了耐久忘了改档位」的状态。

## 它什么时候生成

**回收流程** —— 球靠【空气动力球】飞回来的那一刻（`BallProjectile.deliverToOwner`）：

```
球（用过的）  →  clusterize 套成壳  →  交给袋子 / 背包
```

**套壳排在交付之前** —— 也就是说，**不管身上有没有袋子**，回收回来的球都会先套成壳，
之后才决定进袋子还是进背包。满耐久的球会被 `clusterize` 原样返回（它们本来就能叠成一堆）。

> ⚠️ **这一条在 1.1.0.0 ~ 1.1.0.3 之间是坏的，写在文档里免得以后再犯。**
>
> 原先的写法是「袋子优先，袋子收不下才套壳」。而 `BallPouchHelper.deliverReturned`
> 只要在背包 0..35 里**找到一个空格就返回 `INVENTORY`**，只有**背包也满了**才返回 `NOWHERE`。
> 于是「收不下才套壳」那座兜底**一次都没执行过** —— 球堆从 1.1.0.0 起就是死代码，
> 玩家根本看不到它。
>
> 修法就是把套壳提到交付之前（见上）。**教训：兜底条件要拿实际返回值核一遍，
> 别假设「函数会失败」。**

## 从哪来、怎么用

**只在回收时生成** —— 球靠【空气动力球】飞回来的那一刻（`deliverToOwner`），
**不是「捡起就变」**。

**去向顺序：袋子优先，球堆兜底。**

| 情况 | 去向 |
|---|---|
| 身上有收纳袋、装得下 | 进袋子（满耐久→弹药段，用过→转运段） |
| 袋子满了 / 没带袋子 | **套成球堆** |
| 连背包也放不下 | 掉成掉落物 |

**右键球堆**：耐久从低到高依次取出一颗。取走最后一颗时，壳化身成那颗球。

### 袋子里也按堆存（1.1.0.1 补的）

**收纳袋的转运段直接存球堆** —— 同球种 + 同档位的球进袋时合并成一格。

之前不是这样的：袋子里的球是散球，而 `fillInto` 用
`ItemStack.isSameItemSameComponents` 判断「能不能并进同一格」——
**这和 MC 的堆叠判定是同一条**。用过的球耐久各不相同、组件必然不一致，
于是**每颗必然独占一格**：袋子看着装满了，其实一点没省。

现在：

| 段 | 存什么 | 为什么 |
|---|---|---|
| 弹药段 | **满耐久的散球** | 满耐久的球不带耐久组件，组件完全一致，本来就叠得起来 |
| 转运段 | **球堆（壳）** | 用过的球按档合并，一格装一堆 |

配套的几件事：

- 进袋时按档合并；**旧的散球会在下一次写入时就地转成壳**（旧存档自动迁移，不用手动整理）
- 取球（`takeFirst` / `takeSameKindFrom`）：是壳就掏一颗，壳留剩 —— 原来会**整格端走**，
  把一整个壳当成一颗球交出去
- 「同种」判定（`sameKind`）：先摊开壳再比，否则壳的 item 是 `ball_cluster`、
  球的 item 是别的，永远判「不同种」，弩就装不上袋里的球
- 界面：转运格收壳、shift 搬运把壳搬进转运段
- **tooltip 显示「40 颗（占 3 / 18 格）」** —— 只报格数的话，装了一堆球却显示「1 / 18」，像丢了

**信息显示**：

- **常规信息栏**（不用按 Shift）：`内含 N 颗` / `最低耐久：X`
- **按住 Alt**：改成列出**耐久最少的前 6 颗**的剩余耐久（其余藏起来）
- **图标角落的数字**：壳是 `stacksTo(1)` 的，原版不会画堆叠数字，所以自己挂了个
  `IItemDecorator` 画 —— 坐标逐字照抄原版 `itemCount`，**落点和真·可堆叠物品完全一致**

## 一键整理（1.1.0.6 加的）

**背包界面左侧外沿有个 12×12 的小按钮「整理球堆」** —— 点一下就把背包里的
**用过的散球**按档收成球堆。

- **不依赖任何附魔** —— 球堆原本只在回收时生成，要验证它得先打一场球、还得给弩附魔，
  门槛太高。这个按钮让「机制本身」和「回收链路」可以分开验
- **只动用过的散球** —— 满耐久的不动（它们本来就能叠）、已经是壳的跳过
- **整理规则和回收那条路共用 `clusterize`** —— 不是另写一份，所以两边行为必然一致
- 外观走**原版按钮精灵**（`widget/button`），看着就是原版 UI 的一部分

> **为什么用 `ScreenEvent.Init.Post` 而不是 mixin**：官方事件正好是「界面刚初始化完、
> 可以往里加控件」的时机，不会有版本匹配风险。

## 图标与右键（1.1.0.7 / 1.1.0.8）

**图标 = 里面那种球的图标。** 走的是原版「特殊模型」：json 只声明
`minecraft:special`，真正的绘制由 `BallClusterSpecialRenderer` 完成 ——
它从 `BALL_CLUSTER` 组件里取出那颗球，再按**原版流程**画一遍
（组合球的象限、附魔光效、损坏条都自动跟着走）。

**右键单击**取出**耐久最低**那颗。取走最后一颗时，壳把自己交出去（那一格消失）。

> ⚠️ **空壳右键没有反应** —— 那是刻意的。创造栏直接拿出来的 `ball_cluster` 就是空壳。

## 怎么用

| 操作 | 效果 |
|---|---|
| **手持球堆右键** | **扔出一颗**耐久最低的球（可蓄力的球**有蓄力条**，蓄满再扔） |
| **手持球堆 Shift+右键** | **放进空着的物品栏**一组耐久最低的球（**不是扔**） |
| **背包里右键球堆** | 把**一组**最低耐久的球拿到光标上 |
| **副手持球堆上膛** | 直接从壳扣球装填，**副手全程保持是壳** |
| **主手从弩切走** | 袋子**主动收回**副手那颗球 |
| **鼠标中键** | **整理球堆**（和背包界面那个小按钮同一个作用；可在按键设置里改键） |
| **捡起用过的球** | **自动收成壳**进背包，不用手动整理 |

### 「一组」是什么

**耐久值相同的那一批** —— 不是固定 64 颗，也不是随便一批。

> 依据是作者的两句话：「释放**一组**耐久最低的球」+「显示该耐久的球有几个」——
> 说的是同一件事。`lowestGroupSize()` 从升序的 `balls` 下标 0 往后数到耐久变了为止。

**同一组的球耐久完全相同 ⇒ 组件完全相同 ⇒ 本来就能叠** —— 所以光标上放的是
「一个数量 N 的球」而不是 N 个格子。

### 不留空球堆

壳里**只剩 1 颗**时，那一颗直接顶上这一格，壳消失 —— 不会出现「空球堆」停在物品栏里。

> ⚠️ `ItemStack` 的 item 是 final 的、不能就地换物品，所以「变回球」这一步
> **只能由持有那一格的人做**（`setItemInHand` / `slot.setByPlayer`）。
> 见 `BallClusterItem.declusterInto` 与 `takeOneWithDecluster`。

### 自动补弹的前提

**必须装备了收纳袋。** 本机制的定位就是「袋子里的弹药自动补到副手」——
没袋子就没有「自动补弹」可言，副手该玩家自己管。
## 图标是怎么画出来的（结论靠日志，不是靠推）

球堆的图标 = 「壳 + 里面那颗球的图案」，走 `minecraft:special` + 自定义 `SpecialModelRenderer`。

### 最终写法：`GUI` context + **原样提交**（不加任何 scale/translate）

```java
ItemStackRenderState state = new ItemStackRenderState();
resolver.updateForTopItem(state, inner, ItemDisplayContext.GUI, null, null, 0);
state.submit(pose, collector, light, overlay, outline);   // pose 原样，不动
```

`getExtents` 报 `0..1`（与 `ComboChargeBallRenderer` 一致）。

### 为什么是这样一个组合（日志实测数据）

```
[球堆][诊断] submit 被调用 —— special 渲染器确实在跑；inner=潮汐球
[球堆][诊断] ctx=GUI  isEmpty=false oversized=false 包围盒=AABB[-0.5,-0.5,-0.5] -> [0.5,0.5,0.5]
```

⇒ `state` 内部已经把几何摆成「**以原点居中、±0.5**」，外层那条链给的 pose
再放大 16 倍 ⇒ 半格，**本来就正好**。所以什么都不用加。

### ⚠️ 我踩过的坑，按时间顺序

| 版本 | 做法 | 结果 | 为什么错 |
|---|---|---|---|
| .8 / .20 | extents 给 `±0.5` / `±0.6` | 无变化 | 单位口径错 |
| .23 | extents 用 `visitExtents` 采样 | 无变化 | 它会给变换后的盒子 |
| .28 | extents 改 `0..16` | 无变化 | —— |
| .35 | context 改 `NONE` + 自己 `translate(-0.5)` | **整个消失** | 几何留在 0..16，外层再 ×16 ⇒ 占 16 格，槽位里只剩放大的透明边缘 |
| .43 | 照 `ComboChargeBallRenderer` 加 `scale(1/16)` | **整个消失** | 那个渲染器**自己提交 0..16 的顶点**所以需要缩；`state` 提交的已经是 ±0.5，再缩 ⇒ 只剩 0.5 像素 |
| **.45** | **去掉缩放，原样提交** | ✅ | —— |

**教训**：抄别人的做法之前，先确认「**他缩的是哪一份几何**」——
同样的手法对着不同来源的几何，效果正好相反。

## 袋子内容为什么要手动同步

袋子的内容存在 ItemStack 的**组件**里（`POUCH_CONTENTS`），服务端改组件，
**客户端不会自动知道**。

- **背包 / 快捷栏里的袋子** —— 原版菜单每刻 `broadcastChanges()` 会把变了的槽发出去，本来没问题
- **饰品栏（Curios）里的袋子** —— Curios 只在「栈被换过」（`setStackInSlot`）时才同步，
  直接改组件它完全不知道

后果：`BallPouchHud`（副手栏上方那个弹药格）读的是客户端那份 ⇒ 一直显示旧值，
**要玩家手动动一下袋子里的球才刷新**（作者 2026-10-15 反馈）。

修法：`BallPouchHelper.syncPouchToClient(player)` —— 背包走 `inventoryMenu.broadcastChanges()`，
饰品栏走 `BallPouchCurios.forceSync()`（把袋子原样写回槽位，内容不变）。
在**回收 / 整理 / 补弹消耗**三处调。

## 球堆当弩弹药

作者 2026-10-15 指定：

> 副手持球堆的时候，应当从球堆里扣除一颗**耐久最低**的球上膛，
> 然后球堆减少对应的球，**保持放在副手**。并且这一点要和魔丸收纳袋的补弹相适配，
> **这两个不是独立的机制，要联动起来**。

实现（`CrossbowItemMixin`）：

```
tryLoadProjectiles HEAD:   副手是壳 → takeOne（扣一颗耐久最低的）→ 顶上副手，壳暂存
tryLoadProjectiles RETURN: 装填完 → 把壳放回副手（副手被占就收背包，绝不凭空消失）
```

**⚠️ 为什么不能把壳本身当弹药**：`draw(...)` 返回的 List 里会**装的就是壳** ⇒
整个壳进弹仓 ⇒ 一次发射全没了（作者实测「会错误的直接全部发射出去」）。

## 蓄力是怎么来的

手持球堆右键**可以蓄力**（可蓄力的球才有）。它是复用球本身那条链，不是另写一套：

```
BallClusterItem.use       探测壳里那颗球的 chargeLevels → player.startUsingItem(hand)
BallThrowHandler.onStartUsing   认壳 → setDuration(BallCharge.USE_DURATION)
BallThrowHandler.onStopUsing    认壳 → 取一颗 → BallCharge.levelAt(usedTicks, 等级) → 出手
```

**⚠️ 两个必须注意的点**：

- `startUsingItem` **两端都要调**（蓄力条与 `usedTicks` 都来自原版「使用中」状态，
  客户端不进这个状态就看不到条）
- **Shift+右键 不进蓄力**（那是「放进物品栏」）—— 我漏过这一条，于是 Shift 也走蓄力、
  松开被当普通投掷扔出去

蓄力条本身由壳的 `getUseDuration` / `getUseAnimation` 覆写提供 ——
原版画条读的是**正在使用的那件物品**（= 壳），壳不覆写就画不出来。


## 「几颗」是怎么数的（一个口径错了，六处一起错）

球堆内部的 `balls` 列表，**一个元素 = 一颗球**（`count` 恒为 1）。

> ⚠️ 1.1.0.23 之前不是这样：`withAdded` 把**整个栈**当成一个元素塞进去。
> 而背包里 8 颗同耐久的球是**一个 `count=8` 的栈** ⇒ `balls.size()` 返回 1
> ⇒ 图标角标、tooltip、「一组」的数量、`declusterInto` 的判据**全都显示成 1 颗**。
>
> 修法不是逐处改口径，而是**让口径本身成立** —— 入壳时按 `count` 拆成一颗一个元素，
> 六处一次性对齐。

所以：

```
size()               = 颗数（就是 balls.size()，因为一个元素一颗）
lowestGroupSize()    = 从下标 0 起「耐久相同」的那一批的颗数
lowest()             = 耐久最低的那一颗
```

## 悬停页显示什么

**不显示球名**（球名里已经含球种），显示的是**球本身的详细信息**：

```
内含 12 颗
【基础伤害11】
【坚固3】
【蓄力3】              ← ★ 这一条恒显（见下）
最低耐久：173（共 3 颗）
按住 Alt 查看耐久最少的 6 颗 · Shift+右键 扔出一组
```

格式**直接复用** `BallTooltip.entries` —— 和球本身、径向菜单读的是**同一份**，
将来球改了词条，球堆自动跟着变。

**⚠️ 【蓄力x】在球堆上是常显的**：`BallTooltip` 里那条的显示条件是
「展开 或 蓄力值非默认档」，默认档的球不按 Shift 就**没有这一行**。
那对「球」合理（球主要当弩弹药），但**球堆右键就是蓄力投掷** ——
所以球堆取完整列表后自己过滤：**CHARGE 恒显，其余跟随 Shift**。


## 袋子里的球堆 —— 一条链，六处都要认壳

**球堆不在 `#more_balls:balls` 标签里**（它是容器不是球），所以链路上**每一道 `isBall` 判断都是一道门**。
这条链一次漏一环就断，症状还各不相同：

| 环节 | 位置 | 漏了会怎样 |
|---|---|---|
| 种类键 | `BallAmmoSelection.kindOf()` | 壳的组件各不相同 ⇒ **同种球堆不合并** |
| 数量 | `BallAmmoSelection.collect()` | 用 `getCount()` ⇒ 壳 `stacksTo(1)` ⇒ **数量恒为 1** |
| 选中 | `SelectAmmoPayload.handle()` | `isBall(壳)` ⇒ **选中球堆压根不生效** |
| 找耐久最低 | `BallPouchItem.indexOfLowestDurability()` | 读壳自身组件 ⇒ `MAX_VALUE` ⇒ **壳永远排最后、取不出来** |
| 取出来 | `BallPouchItem.takeLowestDurability()` | `segment.remove(index)` ⇒ **整个壳被当成一颗球交出去** |
| 塞回去 | `BallPouchItem.insertToTransit/Ammo()` | `isBall(壳)` ⇒ **球堆塞不回袋子** |

**统一口径**：

```
判种类     → BallClusterItem.asBall(壳) 摊开成里面那颗球
数颗数     → BallClusterItem.contents(壳).size()
取一颗     → BallClusterItem.takeOne(壳)（壳留剩，掏空了就清掉那一格）
入口判据   → isBall(x) || isCluster(x)
```


## 回收与副手 —— 谁决定副手上有什么

作者 2026-10-15 要求核实这条：「**理论上放到袋子里、当前选取了这个弹药的情况下，
会被直接放到副手**」。核实结果：**确实是这样，而且副手上出现球只有这一个原因。**

### 全链（带行号）

```
【回收】BallPouchHelper.deliverReturned L214
   isPristine(ball)  ← 认壳（摊开判里面那颗球的耐久）
   pristine ? insertToAmmo（备用区） : insertToTransit（转运段）
        ↓
【进袋子】BallPouchItem.insertToTransit L191
   入口接受壳；内部 clusterizeSegment + fillClustered ⇒ 用过的散球在袋里收成壳
        ↓
【自动补弹】BallAmmoAutoLoader.onPlayerTick（PlayerTickEvent.Post ⇒ **每刻都跑**）
   L63  主手不是弩              → 把副手那颗球收回收纳袋 + return
   L69  弩已装填                → return
   L82  身上没袋子              → return     ← 闸门一
   L88  没在轮盘里选过弹药        → return     ← 闸门二
   L114 takeLowestDurability(pouch, wanted)   ← 先查转运段（用过的球在那儿）
   L122 该种类已用完             → return     ← 闸门三（**不会改拿别的种类**）
   L131 旧的那颗先还回袋子
   L144 setItemInHand(OFF_HAND, taken)        ← **往副手写球的唯一一行**
```

### 结论

```
没装备收纳袋        ⇒ 副手不会被塞
没在轮盘里选过种类    ⇒ 副手不会被塞
选中的种类袋里已用完  ⇒ 副手不会被塞，也不会换成别的种类
回收进来的球正好是选中的那种 ⇒ 会被补到副手
```

**⇒ 副手是「装填位」**：

- 唯一的主动填充者 = `BallAmmoAutoLoader`（**按你选中的种类、从收纳袋取**）
- 装填时的消耗 = `CrossbowItemMixin` 从**副手的壳**里扣一颗、壳留剩

### 撤掉过的三处「乱动玩家背包」

这三处**都是我自己加的**（作者从未要求过），症状是「没选弹药副手也被塞 / 装的是别的种类」：

| 位置 | 原来干什么 | 撤于 |
|---|---|---|
| `BallAmmo.swapHeldAmmoForLowestDurability` | 副手空 → 从**背包**挑一颗最低耐久的顶上 | 1.1.0.34 |
| 同上（另一段） | 副手满耐久 → 与**背包**里最旧的同种球**对调** | 1.1.0.34 |
| `BallPouchHelper.giveToPlayer` | 回收的球 → **空的副手** | 1.1.0.37 |

撤完后那个方法的反汇编只剩判断（**`Inventory` 调用 0、`setItemInHand` 0**）：

```
0: instanceof Player ; 15: return
16: getOffhandItem ; 22: isCluster ; 28: return
30: isEmpty ; 36: return
38: isBall ; 41: ifne ; 44: return
45: return
```

**⇒ 模组只从两个地方提供弹药：收纳箱（袋）里的球、副手的球堆。玩家的背包一律不碰。**

### 备用区 vs 转运段（一个判据错了就会分错段）

```
isPristine(球)  = 没有 TOUGHNESS_LEFT 组件  ⇒ 进**备用区**（ammo）
                   有组件（弹过）          ⇒ 进**转运段**（transit）
```

⚠️ **壳自身没有那个组件** ⇒ 直接判会**恒为「满耐久」**，于是用过的球套壳后被塞进备用区
（症状：「收回时球会错误的在备用区变成球堆」）⇒ 必须先**摊开成里面那颗球**再判。

## 它在哪些地方看不到

- **创造物品栏**：创造栏是**标签驱动**的（实时遍历注册表、只收 `#more_balls:balls`）。
  球堆**不挂那个标签**，所以自动进不去 —— 一行代码都不用改
- **JEI 物品列表**：在 `onRuntimeAvailable` 里用 `removeIngredientsAtRuntime` 移除。
  但**注册子类型是保留的** —— 那是「悬停按 R 跳到内部那颗球的配方」的硬性前提。
  子类型**只按球种算、不带耐久**（作者特意交代「不要一次性搞太多条目」）：
  带上耐久会从 18 个条目炸成几十上百个

## 兼容性：老功能一个都没坏

| 功能 | 处理 |
|---|---|
| **弩装填** | 副手是壳时，装填前先掏出最低那颗顶上副手、壳退回背包 |
| **收纳袋** | `insert` 里加壳分支：把壳里的球逐颗倒进袋子，塞不下就放回壳里 |
| **铁砧修复** | 不用动（它用的是自己独立的判据，壳本来就不参与） |
| **拾取** | 不用动（壳不是球，掉在地上走原版拾取、正常进背包） |
| **回收交付** | 不用动（走 `insertToAmmo`/`insertToTransit`，不经过壳分支） |
| **袋子界面** | 转运格 `mayPlace` 认壳、`quickMoveStack` 把壳搬进转运段（1.1.0.1） |
| **袋子存储** | 转运段改存球堆、按档合并（1.1.0.1 —— 原先每颗独占一格） |
| **交付时机** | 套壳提到交付**之前**（1.1.0.4 —— 原先「袋子收不下才套」永不执行，见上节） |

> **弩那处的坑**：光让装填的 predicate 认球堆是不够的 ——
> 原版 `draw()` 装进 `CHARGED_PROJECTILES` 的是**那一格本身的副本**，
> 副手是壳就会把整个壳装进去，于是 `createProjectile` 那边 `isBall(projectile)` 不认、
> 掉进原版兜底，**发射出来是一支普通箭**。所以必须在**装填之前**把副手那一格摊开成真球。
